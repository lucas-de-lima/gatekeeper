# 10 — Implementation Guidance and Acceptance Criteria

## 1. Implementation objective

Build the complete integrated harness described by this blueprint, not a disconnected series of toy demos. Internal engineering work may use tests and sensible milestones, but do not turn delivery into an endless user-facing loop of micro-prototypes and repeated architecture approvals.

The local agent should implement a coherent system, use its judgment on low-risk technical details, and finish with a consolidated end-to-end validation.

## 2. Resolve technical choices responsibly

The blueprint intentionally does not mandate a programming language for the core. The local agent should choose a maintainable approach based on:
- Available local toolchains and executor support.
- Cross-platform Windows/Linux/macOS requirements.
- Simplicity of packaging and portable distribution.
- Ease of integrating agent tools/MCP/OpenTelemetry.
- Existing mature libraries versus custom code.
- Avoiding unnecessary multi-language/microservice complexity.

Document the selection and trade-offs. Do not choose a language merely because one referenced project uses it.

## 3. Required deliverable capabilities

### Core
- Main agent/orchestrator protocol.
- Pipeline definitions and runner.
- Stage executor and direct stage invocation.
- Run state, resume, cancellation and bounded retries.
- Context assembler.
- Artifact manager and schema validation.
- Provider/adapter interfaces.

### Pipelines
At minimum:
- `project-onboarding` (AI-led).
- `feature-development` (full E2E).
- `bug-fix` (repro/diagnose/fix/verify/review).
- `code-review` (review existing diff against spec/standards).

Other useful pipelines such as refactoring, research, and maintenance may be added if not overcomplicating the core.

### Skills
Provide a small curated baseline covering:
- Project discovery.
- Requirements grilling/specification.
- Technical planning.
- TDD/test strategy.
- Debugging/diagnosis.
- Domain modeling/glossary.
- Codebase design/architecture.
- Code review.
- Handoff/retrospective.

Use Agent Skills-compatible packaging where possible. Record lineage/license for adapted upstream material. Avoid full ECC + full Matt Pocock duplication.

### Integrations
- CodeGraph and Graphify integrated as complementary structural-knowledge providers after current upstream and platform validation; track overlap, provenance, and freshness.
- ai-memory adapter or a clear compatibility/fallback state.
- Direct/native model provider, optional OmniRoute adapter.
- OpenTelemetry-compatible tracing with local fallback.
- Optional Phoenix integration.
- Harness²-inspired improvement experiment workflow; evaluate whether to integrate its executable or implement a narrow compatible learning cycle. Do not misrepresent a conceptual adaptation as direct integration.

### Portability
- Upstream versioned repository.
- AI-led project onboarding.
- Project-local `.harness/` instance and manifest.
- Minimal native executor instructions generated by the agent.
- Capability-aware adapters.
- Managed file ownership and safe upgrade/diff.
- `.gitignore` policy separating durable project knowledge from transient local data.
- No absolute machine paths in committed files.

## 4. AI-first onboarding acceptance criteria

Onboarding is not accepted unless:

1. The first orchestration step is performed by the AI agent, not a preflight scanner.
2. The agent can begin with only a reference/path to the harness and the target project open.
3. It reads the bootstrap specification before making changes.
4. It uses progressive discovery and explains material helper operations.
5. No monolithic hidden script performs full discovery, architecture inference, file generation and integration before AI review.
6. It distinguishes observed/inferred/confirmed/unknown claims.
7. It detects existing project instructions and avoids overwriting user content.
8. It creates the project profile and integration files through AI-directed operations.
9. It creates a manifest containing source version/revision/schema information.
10. It reports unconfigured integrations honestly.
11. It validates its generated artifacts and Git ignore rules.
12. The project remains usable after the harness USB/source directory is disconnected, except for explicitly documented external dependencies.

## 5. Pipeline acceptance criteria

1. Run a full feature-development pipeline from task intake to convergence and handoff.
2. Every stage has input/output contracts and status.
3. Direct invocation of at least Discovery, Specification, Verification and Review works when prerequisites are supplied.
4. A failed verification gate triggers bounded diagnosis/retry, not false success.
5. A run can resume after interruption using artifacts/state, not only chat history.
6. Stage outputs link to task/run/repository revision.
7. The pipeline uses the project's discovered commands and conventions rather than a hard-coded stack.
8. No stage is required to spawn its own LLM agent if deterministic work is sufficient.
9. Subagents, if present, have clear delegation criteria and isolation.

## 6. Portability acceptance criteria

1. Core can be cloned to an arbitrary local path or stored on removable media.
2. Onboarding copies/installs only the needed managed files into target project.
3. Project instance does not contain absolute path dependency on upstream/USB.
4. Project-specific profile/overrides are committed to the project's Git history.
5. Transient runs, traces, caches, indexes and credentials are ignored/not committed by default.
6. Manifest identifies upstream version, source revision and schema version.
7. Upgrade preview detects local modifications and never overwrites them silently.
8. At least one executor adapter works end-to-end; other adapters declare tested support and limitations.
9. Windows path behavior and native/WSL dependency support are documented honestly.

## 7. Quality and observability acceptance criteria

1. Each pipeline run has a run ID and root trace or equivalent structured event log.
2. Stage/tool/model operations can be correlated.
3. Secret redaction is implemented and tested for common patterns.
4. Test/build/lint results are deterministic artifacts.
5. Acceptance criteria map to evidence in a convergence report.
6. Phoenix is optional and a local report/log path works without it.
7. Model usage/cost is recorded where the provider supplies it; missing usage is marked unknown, not guessed.

## 8. Learning acceptance criteria

1. A completed run may create a learning candidate, not an automatic production change.
2. Candidate changes are isolated and versioned.
3. A fixed set of evaluation tasks can compare baseline and candidate.
4. Both improvement and regression are recorded.
5. Promotion requires explicit policy; sensitive policy changes require human approval.
6. Accepted changes can be rolled back.
7. Harness²'s role and any direct integration are accurately documented.

## 9. Test strategy for the integrated build

The implementation should use unit/integration tests internally. Final validation should include at least one complete representative repository scenario and one cross-session resume scenario.

Suggested representative scenario:
- Use a small real repository with a build/test command and a recognizable architecture.
- Run AI-led onboarding.
- Ask for a bounded feature or bug fix.
- Inspect spec, plan, context package, changed files, verification, review and convergence.
- Interrupt/resume or switch executor if supported.
- Confirm memory/handoff continuity.
- Inspect trace and final report.
- Confirm no secrets or runtime caches entered Git.

Do not claim universal support based on one executor or one language. Report the actual tested matrix.

## 10. Final report format

At completion, provide:
- Implemented architecture summary.
- Repository/file map.
- Supported executors and capability matrix.
- Integrations: implemented / optional-unconfigured / simulated / unsupported.
- Onboarding instructions (AI-first, conversational).
- Example E2E pipeline invocation and direct stage invocation.
- E2E test scenario, results and evidence.
- Versioning/upgrade procedure.
- Security policy and limitations.
- Known issues and deviations from this blueprint.
- Next recommended work, prioritized by evidence.
